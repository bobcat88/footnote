# ICM comparison and retrieval priorities

Research note, 2026-11-12. This is an evaluation plan and a comparison of documented behavior, not a claim that Footnote is ahead. ICM's claims are vendor-reported, not independently reproduced here.

## What ICM does

[ICM 0.11](https://github.com/rtk-ai/icm/blob/main/README.md) is a Rust memory service with one SQLite store. Its default retrieval combines FTS5 BM25, optional sqlite-vec embeddings and a date-window list with reciprocal rank fusion; project/topic filters apply before the cut. Its default multilingual E5 large ONNX model is about 2 GB according to its README; it supports keyword-only operation and alternate models. [Architecture](https://github.com/rtk-ai/icm/blob/main/docs/architecture.md).

It supports storing and updating memories, session-start/prompt hooks, and automatic extraction. Its README says extraction can send tool output to an installed LLM CLI; provider=none avoids that path. This is materially different from Footnote's read-only MCP boundary and explicit indexing. Any equivalent extraction must be opt-in and preserve that boundary.

ICM reports LongMemEval-S retrieval-only recall_any@5 of 487/500 (97.4%) and recall_all@5 of 443/500 (88.6%), using user turns, one memory per session, about 48 sessions per question, with no date given to ICM. It reports LoCoMo end-to-end answer accuracy using separate answer and judge models. These are different measurements. [ICM benchmark protocol](https://github.com/rtk-ai/icm/blob/main/bench/amb/README.md).

Footnote's current published LongMemEval retrieval figure is a lab pipeline result on 343 held-out questions, not the shipped MCP binary and not ICM's full 500-question run. The local `bench/run_lme.py` excludes abstention questions and constructs each haystack per question; candidate chunking/user-turn handling is engine-dependent. Do not compare percentages until qids, filtering, session mapping, k, ingestion and scorer have been verified equivalent.

## Why SQLite and a high recall score are not contradictory

Our SQLite/Tantivy bake-off and ICM's headline test measure different things. `bench/dbbake/track_a.py` measures lexical BM25 engine retrieval and warm per-query latency on SciFact/mixed text and synthetic corpora; it does not run ICM's complete memory pipeline. On SciFact, FTS5 Porter scored 0.6874 nDCG@10 versus Tantivy English 0.6868 in those runs (roughly equal), while their p50s were 3.78 ms and 0.08 ms. At 1M synthetic documents, the FTS5 and Tantivy p50s were 422.78 ms and 3.0 ms. The first result is judged retrieval quality; the latter is a speed-only scale measurement. Faster text indexing does not itself guarantee higher relevance.

ICM v2 retrieves candidate lists independently: FTS5 OR/BM25, sqlite-vec cosine KNN when embeddings are enabled, and a date-window arm for time-specific questions. It fuses their ranks with RRF k=60 and can append related-memory neighbors after the cutoff. Its documented default model is multilingual-e5-large-onnx (1024 dimensions; roughly 2 GB download), whereas Footnote uses two 384-dimensional models. These mechanisms and model choices, not the SQLite file format by itself, can affect ranking. [ICM architecture](https://github.com/rtk-ai/icm/blob/main/docs/architecture.md) and [README](https://github.com/rtk-ai/icm/blob/main/README.md).

The specific 97.4% ICM recall run makes one fresh index per question with roughly 48 historical sessions and user turns only, without supplied dates; it includes all 500 cleaned questions, including abstention-tagged ones, using answer_session_ids as gold. Footnote's current runner explicitly excludes `_abs` questions, and the 97.1% figure is from a 343-question held-out lab run. The two scores, corpus sizes, units and execution paths do not demonstrate that either system is better or faster than the other. [ICM recall-only protocol](https://github.com/rtk-ai/icm/blob/main/bench/amb/README.md).

A useful diagnostic is a 2×2 ablation under identical data: FTS5 versus Tantivy for the lexical arm, crossed with identical dense candidates and identical fusion. Then vary RRF versus Footnote's z-score combination, and only then vary embedding model. Record candidate recall and end-to-end latency at ~48 sessions and at 100k/1M independently. This identifies which layer causes any gain. Preserve the existing dev/held-out split and do not use ICM's published number as a substitute for a controlled run.

## What the existing data says

- On full public test sets, shipped Footnote reports nDCG@10 0.7467 SciFact, 0.367967 NFCorpus, 0.478421 Alloprof, 0.795188 Syntec, 0.488989 mixed. Published MTEB model results on those datasets use different runs and may use different preprocessing: they are not controlled competitor measurements.
- Retrieval@20 exceeds retrieval@10 by 0.0290 SciFact, 0.0314 NFCorpus, 0.0587 Alloprof and 0.0538 mixed. This shows more judged relevant material appears within 20 than 10; it is not proof a reranker can move it up without regressions. NFCorpus relevance is multi-document, so recall is not directly comparable to single-answer tasks.
- The current binary scans dense vectors for up to 50,000 entries. Beyond that it rescores a lexical top-1,000 shortlist. It may miss purely semantic or cross-language matches absent from that shortlist; the impact on judged quality at 100k+ is unknown. E13 remains unrun. Existing 100k scale timings use random document vectors and establish speed only.
- Earlier experiments already rejected lexical pseudo-relevance feedback, query-term pruning, dense Rocchio feedback and one adaptive fusion rule on the tested dev sets. The cross-encoder gain on Alloprof dev cost 1–3 seconds per query. Avoid assuming those same methods will generalize.
- The 1M document storage artifacts were 303.9 MB (Tantivy) and 1,714.7 MB (FTS5 database). Their contents differ: FTS5 stored document bodies; Tantivy stored IDs and search structures without bodies. Neither figure includes the complete Footnote store, embeddings, models and runtime. This is not evidence of a 5.6× smaller total database.

## Proposed experiments, before looking at results

1. **Like-for-like ICM comparison first.** Freeze ICM version/commit, Footnote executable hash and model files. Use the same permitted local LongMemEval data, question IDs, user-only turns, session boundaries, no extra dates, top-k and scorer. Run keyword-only and configured hybrid for each where supported. Record failures, exact settings, output hashes, nDCG, any/all recall@5/@10, per-type breakdown, ingestion and warm/cold p50/p95, peak RSS, complete disk artifacts and model sizes. Run repeated trials on the same machine without other heavy jobs. Inspect the 500-question eligibility and abstention semantics rather than forcing a count. Do not run remote model calls or upload local content.
2. **Full footprint accounting.** Compare reproducible stores built from identical documents and update/delete workloads. Report source store, derived index, vectors, WAL/temp files, embeddings, executable, model weights, process RAM and build peak separately. Compare equivalent retained content and semantics. Retain test artifacts and raw size manifests.
3. **E13 semantic recall above 50k.** Evaluate 100k real-text distractors and judged bilingual/paraphrase queries against the full-scan reference. Compare lexical shortlist 1k/5k and an independently generated dense candidate path. Report gold recall before fusion, final nDCG, p50/p95, memory, build cost and failure cases. Use dev for parameter selection and frozen heldout for confirmation.
4. **Temporal recall inspired by ICM.** Only for datasets with explicit dates and gold temporal relevance: evaluate a third, optional date candidate list in RRF against current fusion. Compare identical input and controls without dates; never infer dates from fabricated metadata. Report temporal and non-temporal regressions, privacy and latency. A material improvement must survive heldout bootstrap.
5. **Target hard misses before larger models.** Slice shipped results by query type, relevant-candidate rank and language. Test a small rerank pool only after measuring its candidate oracle, and compare against the existing E12 latency budget. Keep the fast default if gains are too costly or inconsistent.

Acceptance follows `PLAN.md`: pre-register settings, tune only on dev, evaluate heldout with paired bootstrap, measure costs alongside gains and refuse to claim a general winner from a single dataset. Changes in ranking or storage require implementation tests and production-binary receipts. Nothing in this note has been implemented or benchmarked against ICM yet.
